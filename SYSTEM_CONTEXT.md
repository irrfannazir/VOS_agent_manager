# AOS v0.0.3 — System Context for Agents

This document gives a new agent everything it needs to understand how AOS v0.0.3 works: the pipeline, the two core abstractions (Capability DNA and the Capability Registry), and how models/resources are chosen dynamically per subtask.

AOS is a lightweight agentic microkernel. It decomposes a user prompt into a **task graph** (a DAG of nodes), annotates each node with a typed requirement vector called **Capability DNA**, then binds each node to a concrete resource at runtime via the **Capability Registry**. Nodes execute wave-by-wave (topological order) with concurrency inside a wave, and a failure manager wraps every call in a detect → classify → recover loop.

---

## Core Components

Pipeline entry point is `main.py:run()`:

```
ManagerAgent        decomposes prompt → Graph (DAG of Nodes)      agents/manager_agent.py
DNAExtractor        maps each node → Capability DNA (flags+ordinals+confidence)   dna_extractor.py
ConstraintPolicy    derives each node's constraint segment (kernel-owned)         constraint_policy.py
CapabilityRegistry  two-stage binding: feasibility filter + Pareto scoring        capability_registry.py
GraphExecutor       runs waves concurrently, feeds parents' outputs to children   agents/graph_executor.py
SubAgent            one per node: routes it, then runs it under FailureManager    agents/sub_agent.py
FailureManager      detect → classify → recover around every node call            failure_manager.py
IntegratorAgent     collects sink nodes → labeled final output                    agents/integrator_agent.py
Capabilities/       the actual run functions (web_search, summarization, synthesis, vision)  capabilities/
```

The pass order (see `main.py:run()`):

1. **ManagerAgent** (`create_plan`) — LLM decomposes the job into a graph with function-calling, restricted to capabilities `web_search`, `summarization`, `vision`. It is validated structurally (cycles, dangling deps, duplicate ids) and for semantic completeness (every named entity covered); both have up to 1 automated retry. The kernel then appends a terminal **synthesis** node (`final`) wired to every leaf — the planner is never asked to emit it (`manager_agent.py:_append_synthesis_node`).
2. **DNAExtractor** (`extract_graph`) — fills `node.dna` for every node except the kernel-authored synthesis node (which ships with its DNA pre-set, `extracted_by="kernel"`).
3. **ConstraintPolicy** (`apply`) — overwrites the `constraints` segment of every DNA from the job budget + live resource pool. Constraints are kernel-derived on purpose; a model once invented `latency_slo_ms: 500` for every node, which made everything infeasible (see docstring in `constraint_policy.py`).
4. **Admission control** (`_check_satisfiable`) — fail-fast before execution if the registry provides no resource for some required flag.
5. **GraphExecutor** — topologically sorts into waves, runs each wave's nodes concurrently via `ThreadPoolExecutor`, and passes each node's labeled output to its dependents. Vision output is injected into all downstream non-vision nodes so image context is never lost (`graph_executor.py:67-75`).
6. **SubAgent.perform** — the per-node decision maker. Routes the node (DNA two-stage binding, or exact-match fallback), then hands the call to `FailureManager.execute` for the closed recovery loop.
7. **FailureManager** — detects broken output (empty, too short, refusal, corrupt, exception), classifies it, and walks a recovery ladder (retry same → retry with reformulated feedback → resource substitution using the scorer's ranked runner-ups). Exhausted ladders mark the node `degraded` and emit an explicit gap marker.
8. **IntegratorAgent** — concatenates the labeled outputs of all sink nodes into the final answer.

A plan artifact is always written to `outputs/plan.md` — a node table, per-node DNA detail, wave breakdown, and a **deterministic** Mermaid diagram generated by `diagram_utils.build_mermaid()` (never by the LLM).

## Capability DNA

Defined in `models.py` (`CapabilityDNA`), per DOC1 §5.2. It is a **per-subtask requirement vector** — what the subtask *needs* — not a per-resource fit score. Three segments plus provenance:

### 1. `flags` — discrete capability identifiers

Dotted `family.specific` names from one fixed vocabulary (`CAPABILITY_FLAGS`, `models.py:20-40`), e.g. `web.search`, `text.summarization`, `reasoning.deep`, `vision.understanding`, `answer.synthesis`, `code.generation`, `db.query`. Both sides must draw from this single vocabulary: a subtask's DNA lists the flags it **requires**, a resource's manifest lists the flags it **provides**, and the feasibility filter is set containment over them.

### 2. `ordinals` — difficulty scores (0–4)

`DNAOrdinals` with five axes (`ORDINAL_FIELDS`, `models.py:44-50`): `reasoning_depth`, `planning_horizon`, `tool_complexity`, `memory_dependence`, `parallelizability`. `demand()` (`models.py:81-91`) folds the first three into a normalized 0–1 difficulty score — `parallelizability` is a scheduling hint and `memory_dependence` is state plumbing, so neither feeds demand.

### 3. `constraints` — continuous execution constraints

`DNAConstraints`: `cost_ceiling_usd`, `latency_slo_ms`, `min_quality`, `risk_tolerance`. Defaults are permissive so an un-extracted node still executes. This segment is **kernel-owned** (`constraint_policy.py`), not model-invented:

- **Cost** — the job budget divided across node count, floored at the cheapest capable resource's price.
- **Latency** — slack × the worst p95 among flag-relevant resources (or job SLO ÷ node count).
- **Quality** — linear in ordinal demand across a `[0.45, 0.85]` band.
- **Risk** — a node reaching outside the kernel (`web.search`, `tool.calling`, `db.query`, `sensor.reading`) gets `risk_tolerance="high"`.

`effective_min_quality()` (`models.py:137-145`) takes the max of the declared `min_quality` and the ordinal `demand()` — so a high `reasoning_depth` raises the quality bar even if the planner left the floor at its default. This is what gives ordinals real teeth in the feasibility filter.

### Provenance

`confidence` (0–1) and `extracted_by` record how the DNA was produced — the model name, or `kernel` (the synthesis node), or `heuristic` (offline keyword fallback). They drive escalation and appear in plan.md/traces.

### Extraction process (`dna_extractor.py`)

- A **cheap model** (`llama-3.1-8b-instant`) extracts first via a schema-constrained tool call (`temperature=0.0`).
- If it fails or `confidence < 0.7`, a **strong model** (`llama-3.3-70b-versatile`) re-extracts; the more confident vector wins.
- If both fail, a keyword heuristic produces a conservative DNA (`extracted_by="heuristic"`, confidence pinned low). The pipeline never hard-fails on extraction.
- Out-of-vocabulary flags are dropped rather than raised; any hallucinated `constraints` key is ignored outright.

## Capability Registry

`capability_registry.py`, per DOC1 §5.1/M5.

### Resource manifests

Every resource publishes a `CapabilityManifest` — a pure, serializable declaration: `resource_id`, `resource_class` (`llm`, `vlm`, `asr`, `tool`, `api`, …), `capabilities` (from the shared flag vocabulary), input/output schemas, `cost_model` (`estimate_usd`), `latency_model` (`p50_ms`, `p95_ms`), `quality_priors` (per-flag quality estimates, hand-calibrated initially, later learned), `availability`, and `risk_class` (`low|medium|high`). The actual callable lives in a parallel `run_fns` dict on the registry — the manifest stays serializable.

The default pool (`resource_registration.py:build_default_registry`):

| resource_id | class | notable flags | cost | p95 |
|---|---|---|---|---|
| `web_search` | tool | web.search, tool.calling | $0.004 | 9000ms |
| `summarization` | llm | text.summarization, **reasoning.deep**, planning.decomposition | $0.003 | 5000ms |
| `vision` | vlm | vision.understanding | $0.00 | 15000ms |
| `synthesis` | llm | **answer.synthesis**, reasoning.deep, text.summarization | $0.006 | 9000ms |
| `quick_summarization` | llm | text.summarization, text.classification (no reasoning.deep) | $0.001 | 2200ms |

Resource ids deliberately match the coarse v0.0.2 capability strings so one `register()` serves both the DNA path and the exact-match fallback.

### Two-stage binding (`CapabilityRegistry.select`, M5)

1. **Feasibility filter** (`feasible`) — a resource survives only if: availability is `up`; its `capabilities` are a superset of the DNA's flags; its `risk_class` is at or below the subtask's risk tolerance; its cost is within the ceiling; its p95 is within the SLO; and its mean quality prior clears `effective_min_quality()`. Every rejection records its **first** violated constraint (checks short-circuit cheapest-first).
2. **Pareto scoring** (`score_candidate`) — over the survivors:

   ```
   score = quality_prior − λ·cost_norm − μ·latency_norm
   ```

   where `λ = lambda_cost = 0.3`, `μ = mu_latency = 0.2`, and both terms are normalized against the **subtask's own** ceiling and SLO (so they are commensurable and in [0,1] for anything that passed stage 1). The winner is the max score, tie-broken by `resource_id` for deterministic seeded replay.

`select` returns a `ScheduleDecision` — an audit record of the winner, its score, quality, cost, latency, the ranked candidate list, the rejection reasons per resource, and the runner-up + margin. `bind` returns the decision plus the callable the executor needs. `unsatisfiable_flags` feeds admission control: the pre-execution hard rejection that names a capability the pool simply cannot provide.

The scorer is deliberately rule-based; the planned contextual bandit plugs in at `score_candidate` without touching stage 1.

## Dynamic Model Selection

"Model selection" here is **per-subtask, at runtime**, decided by the Capability Registry against the node's DNA — and it is not just "pick a model": it picks the whole resource (model + tool + cost + latency), then adapts again on failure. The rough model IDs live inside each capability module (e.g. `capabilities/summarization.py:_MODEL = "llama-3.3-70b-versatile"`, `vision.py` → local Ollama `medgemma1.5:latest`, `web_search` → DDG search + extraction LLM pass).

### Where selection happens

- **`SubAgent._route`** (`agents/sub_agent.py:64-111`) is the decision point. If the node has DNA flags → `registry.select(dna)` (two-stage binding above) → `bound_resource` and `routing_mode="dna"`. If the node has no DNA, or the DNA is infeasible, it degrades to **exact-match** on the coarse capability string (`routing_mode="exact"`), mirroring v0.0.2.
- The ranked feasible list is the **substitution ladder**: `FailureManager.execute` walks `candidate_ids` in score order, so a failing node retries on the runner-up the Pareto scorer already vetted — not an arbitrary sibling.

### Dynamic aspects (why it is "dynamic")

- **Input-dependent:** the choice varies with what the DNA says. A summarize node under a loose budget binds `summarization` (high quality); the same node under a tight budget (or a cheap plan with many nodes) binds `quick_summarization`; a compare/analyse node requiring `reasoning.deep` can only bind `summarization`/`synthesis` since `quick_summarization` lacks that flag. The terminal node binds `synthesis` because only it provides `answer.synthesis` (`manager_agent.py:283-298`).
- **Constraint-driven:** the per-node cost ceiling = job budget ÷ node count, so a wide graph automatically routes to cheaper resources without any model ever seeing the budget.
- **Escalation on uncertainty:** the DNA extractor itself is a routed resource — cheap model first, escalate to the strong model only on low confidence (`dna_extractor.py:180-211`).
- **Failure-driven re-selection:** when output is detected as broken, the FailureManager classifies the failure and may swap the resource mid-wave, retrying with a reformulated instruction or moving to the next ranked candidate.

### Summary of the selection decision

For each node, exactly one of these binds it to a resource:

1. **DNA routing** — feasibility filter → Pareto score (`score = quality − 0.3·cost_norm − 0.2·latency_norm`) → winner. (Preferred path.)
2. **Exact-match fallback** — coarse `node.capability` → keyed lookup. Used when there is no DNA or the DNA is infeasible.
3. **Failure substitution** — the recovery ladder moves to the runner-up resource while the node is already executing.
4. **Kernel-authored binding** — the synthesis node's DNA is written by the kernel with `extracted_by="kernel"` and is never re-extracted, guaranteeing it binds to `synthesis`.

The routing summary printed at the end of every run (see `main.py:_print_routing_summary`) shows each node's `routing_mode`, `status`, `bound_resource`, and DNA flags — a quick way to verify what was selected and why.
